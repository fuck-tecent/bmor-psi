# 研究路线与命题发布

## 自动继续拆题

维护者说「继续拆剩下的困难命题」时，主动完成一轮选题、推导、编写和校验。默认研究台为 `goldbach`。指定多个研究台时逐台取快照，分别建立依赖图。复跑时从新的缺口开始。

1. 在与最新 `origin/main` 对齐的研究分支上，从根目录运行 `python .agents/skills/goldbach-research-tasks/scripts/frontier.py --problem goldbach`。输出列出全部未获 ACCEPTED 的题、领取状态和显式依赖它的开放题。排序只帮助浏览；结合路线、最近的证明尝试和开放中的任务 PR 选择数学瓶颈。已有人做的父题仍可拆出独立输入，保留其租约和冻结声明。快照不可用时可用 `--snapshot <已保存的该台状态.json>` 做离线草案，发布前重新取样。
2. 从父题结论**反向推导**。写出能推出它的一步，再逐个寻找该步的输入。按 ID、Lean 声明、数学等价形式和在审 PR 查重。对已证输入引用原 ID，对已有未证输入指出尚缺的估计。对确实缺失的输入才拟新任务，并说清这个输入为何更容易着手，例如它移除了哪个耦合条件或能应用哪个已有引理。覆盖多个参数或有限区间本身不能作为全称命题的归约。
3. 对已有输入可运行 `frontier.py --parent <父题ID> --input <输入ID> --input <另一个输入ID>`（用上一条命令的脚本路径和同一分站）。它校对同台冻结声明，输出输入状态及精确的 Lean 候选类型 `(A) → (B) → (父题)`。新增输入也按同一方式将冻结类型括起。先尝试构造这个组合证明，例如给出误差分配、共用阈值和最后一个不等式。核对量词次序和前提是否同时可得。组合只能推出弱结论时，标记 `input` 或 `exploration`，写明反向推导在何处中断。
4. 每次递归都先做下方的数学审核，再决定哪些叶节点值得单独领取。记录已访问的 ID 和声明，拦住循环依赖；叶节点有明确的证明切入口即可停止展开。
5. 有可交付任务时，按 v1 协议准备变更集和 PR。在 PR 正文用一行列出每个候选的 ID、类别、审核依据和去向（新增、复用或仅记录瓶颈）。类别属于研究评审意见，沿用 v1 原有字段。用一句数学结论概括**已经核验了什么、还缺哪个估计**。任务数仅用于统计工作量。所有输入和组合都有证明时，按原冻结声明提交父题，等待权威裁决。

## 超越前人结果的发布标准

每个拟公开领取的任务都须单独通过以下两项审核，包括探索、工具、证伪和组合任务。整条路线的预期贡献不能代替单题证据。先在草案中审核，再把合格题写入 v1 变更集。

1. **严格强于哪条公开定理？** 按冻结 Lean 声明检索原始论文、后续改进和可复核的公开证明。记录检索日期、最接近的可比结果、原文链接、版本及定理号或页码。对齐对象、权重、量词、假设、尺度、常数与误差。写出从候选结论恢复基准定理的推导，并指出一个有数学意义的新增情形或更强的界。再反向检查已知定理及其标准推论能否给出候选结论。增加假设换取更强结论、只改善一个指标同时削弱另一个指标、首次 Lean 形式化或仅超过仓库旧题，都不足以单独通过。声称可证伪时，要给出拟证明的否定命题及其改进基准。
2. **它怎样推动父猜想？** 指明父题 ID、可复用的已证输入，写出代入候选结论后得到的不等式、阈值或被排除的障碍，再指出剩余缺口。哥猜例外集路线要说明界作用于哪些偶数；反复在全体上得到正比例覆盖，不能据此声称上一轮漏点减少。

在发题或审核发题 PR 时，按任务 ID 附上这两项证据。原文无法核对、两个定理不可比、候选已被文献覆盖或下游推导缺失时，该题留作研究笔记；已知工具直接引用。混合批次剔除未通过者，并重新核对剩余题的依赖。全部未通过时发布零条，不创建题单 PR。准备合并时若冻结声明或对标文献有变化，重新审核。发题时使用“待证；若成立将改进某定理”的表述；正式证明须经 Lean 权威核验，文献优先权另按检索范围说明。

例如，若短窗候选限制一个素数在平方根区间，仅得正比例覆盖，而文献允许两个自由素数并得到几乎处处覆盖，应先判为不可比。只有找到同类受限加数定理并给出严格改进与父题用途，才进入公开题单。

## 发题门槛：每题推进一个明确瓶颈

先锁定父命题的冻结声明和当前最小未解估计。逆向写出依赖链：**已证输入 + 新中间猜想 → 可检验的下一步 → 父题的具体瓶颈**。每个候选都要通过以下审核。

1. **结果有用途。** 写出下游任务 ID、它缺的量或条件，以及新结论在同一参数范围内能兑现的阈值、常数、误差预算或被排除的证明机制。探索题可以只推进一部分，但要写明它能确实推出什么、下一步还缺什么。
2. **难点实质降低。** 展开定义后比较量词、参数尺度和前提。可拆成彼此独立的误差项，控制明确的子区间或局部结构，或先研究允许例外的结论。写出至少一种具体攻击方法或寻找反例的办法。若新前提仍要求同一个未知量满足同样的界，沿用原题。
3. **已有成果先用起来。** 查本台已核验声明、Mathlib、在审 PR 和公开文献。能直接调用已有证明、由常规改写或几行算术完成的步骤，放进组合证明或证明提示。新题应当包含现有工具还未解决的数学工作。两条不同方法如果实际要求同一个估计，只发一次。
4. **证伪也要推进。** 可发布一个可被严格反例检验的中间猜想。说明如果失败，会否决哪条正在尝试的推理、哪些假设必须在反例中保留，以及下一步该加强什么。教材式反例、有限枚举、恒等式、定义展开、容易的等价编码和薄接口不得单独发题。必要的接口写入组合证明。
5. **核验组合。** 对标为充分归约的链，提交能赋给冻结组合类型的 Lean 证明并跑固定工具链检查。缺少恢复单点、去掉条件或覆盖剩余尺度的步骤时，将结果标成探索输入。只要反向推导没有给出，就不要断言等价。

PR 正文为每个新任务记录父题瓶颈、可调用的已证输入、待证的新估计、证明或证伪切入口和成功后可推出的结论。缺少任一项时继续找分解或只记录瓶颈。**发布数量由合格候选决定，允许本轮发布 0 条。**

例如，轨道各自均匀却不相遇的反例可作为背景。要继续发题，应提出一个针对实际素数路径的联合分布估计，写清适用尺度，并说明怎么用已证的漏点能量引理把它转成漏点上界。应用能量引理的机械步骤随归约提交。

## 逐题拆解与批量发布接口 v1

生成 v1 JSON 后，使用同一脚本的 `--problem <研究台> --check-plan <变更集.json>`，同时执行下方的 Schema 校验。脚本核对基线、冻结哈希、重复题、依赖环和每个新题到父题的路径，并为充分归约输出预期的组合类型。若 `matches_literal_type` 为 false，在固定版 Lean 中检验实际组合定理能否赋给预期类型，必要时补一条适配引理。图检查与字符串匹配都不能证明这个定理。

所有问题共用[变更集 JSON Schema](../../../research/schema/change-set.v1.json)；每次拆解选择一个研究台、一条父命题。参照[次弧拆解示例](../../../research/schema/example-minor-split.json)，示例供校验，不加入任务队列。

1. **读取**：从研究台快照取得父题 ID、冻结声明和基线 Git SHA。对原声明 UTF-8 字节计算 SHA-256。读取父题、已完成输入和在途任务，先查重。
2. **拆解**：将数学家的意图写入 `motivation`。每条子题给出独立 Lean 声明、显式前提、中英文解释、证明提示、所属路线、来源和依赖 ID。用 `links` 指向下游：`input` 提供必要步骤或可复用输入，`exploration` 是探索，`sufficient_reduction` 要列全输入并提供组合引理 `bridge`。检查组合引理的类型确实把这些输入推到父题。证明状态始终读取权威流水线裁决。
3. **校验**：先用 Draft 2020-12 验证 JSON 结构，再验证父题哈希、ID 唯一性、引用在本台存在、路线存在、依赖无环和双语语义。服务端从 ID 派生固定文件名与模块名；v1 新题使用 Mathlib 并遵循该台的 program/role 规则。对已合入的依赖按下文登记可导入引理；新路线需要扩展协议；v1 的 `route_note` 更新父题对应路线的双语说明。仅调整说明时允许空任务列表。最后运行仓库目录测试和固定版本 Lean。
4. **交付变更 PR**：将变更集落实到对应目录，在功能分支提交并推送。用 PR 正文记录父题、数学动机、新增命题、依赖关系、声明变化和待解决输入。检查通过后，使用当前有目录发布权限的 GitHub 账号 squash 合并，并继续跟进发布。只有遇到权限不足、核验失败或明确要求只提交草案时，才暂停并报告状态。研究目录发布器核对合并身份和 main 上确切 SHA 的 `Goldbach CI / catalogue release` Check。变更集是 skill 的逐题交换格式；发布入口是 GitHub PR。

## 定位缺口

从仓库根目录运行命令。用 `git fetch origin main` 核对研究基线，保留其他维护者的工作树改动。查询主站 `/api/catalogue-status` 或分站 `/problems/<slug>/api/catalogue-status`，按 `gaps[].proved` 查看已证与开放命题。结合 `desk.assignments` 查看在途任务。记录取样时间、目标 ID、冻结声明和已经可复用的结果。用户只要方案时，到路线建议为止。

读父命题的 Lean 原文，逐项核对量词、参数范围、显式假设和最终结论。给每个子题说明它向下一步提供哪个估计、恒等式或构造。把容易并行的输入、组合输入的归约、仍然困难的目标分别标明。几个估计需要同时成立时，统一尺度、权重、阈值和误差预算。例如可将二次素因子中段质量分为两个互斥带，证明分割恒等式，分别研究一个最终一致上界和一个无界多尺度上界，最后证明它们可以在同一尺度合并。

调整方向时在路线里记录目前最缺的输入。借用论文或上游 Lean 工程时，给出原文或固定提交中的具体声明，并区分直接可调用的结论和借用的证明方法。涉及 RH、GRH 或其他猜想时，把前提写入正式命题。若发布参数族，报告族数、实例数、参数选择和共用的一般引理；拆解核心难题时优先寻找实质不同的中间步骤。

## 编辑研究台

新增任务先按[分目录发布约定](../../../research/problems/README.md)放进所属研究台、路线的 tasks 目录。每个 ID 单独建文件。数学依赖通过 `depends_on` 记录。全站已验证社区模块可跨题引用。用 imports 推荐与本题直接相关的模块。运行 `python research/build_catalogue.py --write` 后一并提交生成清单。已发布任务和在审 PR 沿用原路径。以下字段和验证约定两种格式共用。

- 哥德巴赫主站使用 [gaps.json](../../../research/gaps.json) 中的 `gaps`、`tracks` 和 `feeds`。每道新题关联有效的 `track`、`program` 和适当的 `role`。主线数学方向改变时更新 [ROADMAP.md](../../../research/ROADMAP.md)，并核对中英文首页的路线摘要。
- 分站使用 [problems.json](../../../research/problems.json) 对应 slug 下的 `gaps` 与 `roadmap`。在阶段的 `tasks` 中引用同一分站的题目 ID，并为阶段和任务填写中英文文本。只改阶段顺序、说明或引用时，可保留原有题目。
- 遵循同分支相邻记录的字段和 [目录测试](../../../research/test_catalogue.py)。新任务 `L-goldbach-example` 对应模块 `Conjectures.Goldbach.Example`、文件 `lean/Conjectures/Goldbach/Example.lean`。任务生成器派生新任务的 `module` 和 `file`。全站 ID、模块名和文件路径须唯一。填写完整 `statement`、两种语言的 `plain_statement` 与 `brief`、可核对的 `source`，所有新任务填写 `"parallel": true`。使用项目允许的导入。
- 既有领取记录绑定声明字节的 SHA-256。扩充目录时对比基线，核对旧题 ID 和声明。修正改变数学含义的已发布命题时使用新 ID，在路线中解释替代关系并处理旧任务的在途领取和历史记录。仅重写路线说明不需要换 ID。

## 并行领取与积分

所有开放命题都允许不同参与者同时领取并独立提交。有在途尝试时仍可领取。发布前核对新任务源包含 `"parallel": true`，发布后核对状态接口的 `gaps[].parallel`。

积分以服务器登记提交时的分值为准，归首个通过权威 Lean 核验的解决结果。已登记的证伪和原题证明共享一次奖励。题单和 PR 说明应指引参与者优先解决高分题。

## 新版路线图的挂载与验收

新增任务或改路线时，按[新版路线图指南](references/roadmap-display.md)核对主站地图与分站路线面板各自的数据字段和直达链接。PR 写明研究台、路线 ID、影响的任务和中英文预览入口。发布后核对实际页面、任务详情和状态接口中的路线归属。目录测试和 CI 通过后，仍需完成这一步。

单条证明 PR 只提交指定的 Lean 文件。通过权威核验后，页面从任务台状态刷新进度。证明改变研究方向时，由维护者另开路线 PR。

## 把已证 Lean 引理交给领题者直接用

选题时按数学对象和 Lean 声明找依赖。核对线上权威裁决、可信基线中的证明源码和实际定理类型。把同台的直接依赖写入 `depends_on`，运行 `python research/build_catalogue.py --write`，逐个核对生成的 `imports`。任务清单可推荐直接依赖。未获核验或尚未进入基线的输入只登记依赖。无需为了复用而再发一个相同引理，也不要假定任意仓库模块都已授权导入。

在双语证明提示中提醒 Agent 可以导入仓库已核验的引理，所有题目均可跨题、跨猜想引用全站已验证模块。到 https://jenkins-hook.goldbach.tech/verified-imports.json 搜索模块名，在 Lean 文件顶部单独写一行 import <模块名>。gap.imports 列出本题推荐的社区模块及允许的其他项目导入。社区模块直接和间接依赖合计最多 16 个。提示正文无需逐个列出模块或定理。核对使用时的尺度、权重和常数与原定理一致。组合任务在固定工具链检查一份实际调用该定理的证明。上线后从任务详情、领取响应或状态接口核对允许导入的模块。冻结声明继续遵守现有检查器的声明规则。

## 验证、发布与回读

1. 运行 `python research/build_catalogue.py`、`python -B -m unittest research.test_catalogue research.test_route_sources deploy.test_landau` 和 `git diff --check`。人工核对中英文描述与 Lean 类型是否一致，尤其是自然数减法、整除、求和括号和存在量词。若实际需要导入其他已证引理，核对它已存在于受信基线，提交者能够按导入规则使用。
2. 参照 [Desk 测试](../../../deploy/test_desk.py)，用临时 SQLite 初始化各受影响的 Desk，调用 `/api/desk/claim`，逐一验证新增 ID 返回 201 且领取对应题目。验证过程使用隔离租约。
3. 创建 PR 后核对 `Goldbach CI / catalogue PR`，修正在预检中发现的问题。完成数学审核和仓库检查后，用项目所有者或获授权的数学任务发布者账号 squash 合并到 main。默认继续执行下一步，直到线上题单回读成功。
4. 合并后查看该 SHA 的 `Goldbach CI / catalogue release` 和网站 `research-changes`，检查生产快照里的新增 ID 和冻结声明。需要诊断发布时参见[自动发布运维](../../../deploy/catalogue-release.md)。不要把 PR 检查通过或合并动作单独报告为已上线。
5. 给出 PR、CI、受影响研究台与任务链接。区分目录类型检查与提交者的 `Goldbach CI / formal Lean verdict` 及任务台裁决。
